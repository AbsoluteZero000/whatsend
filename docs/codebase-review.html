Security and account isolation

1

Enforce token ownership on every job write

Critical

Problem Job creation and editing trust the submitted token_id. The scheduler later loads that token by ID without confirming that the job and token belong to the same user.

Impact An authenticated user who guesses another token ID could schedule messages through another user’s WhatsApp connection.

Fix Before writing a job, query Token.id == token_id, Token.user_id == current_user, and Token.is_active. Repeat the ownership guard inside the scheduler as defense in depth. Consider a database-level composite constraint.

Evidence: app/routers/jobs.py:280, app/routers/jobs.py:616, app/services/scheduler.py:49

2

Remove HTML-string construction from the group picker

Critical

Problem Group IDs and names from manual input or Whapi are concatenated into HTML and inserted with insertAdjacentHTML.

Impact Crafted group data could inject attributes or executable markup into the authenticated page.

Fix Create each hidden input with document.createElement('input') and assign its value property. Serialize initial server data with Jinja’s tojson filter.

Evidence: app/templates/jobs/form.html:213–238

3

Harden browser authentication

High

Problem Passwords have no server-side strength requirement, login and signup have no rate limiting, cookies omit Secure, state-changing forms have no CSRF token, and sign-out uses GET.

Impact This increases exposure to credential stuffing, weak accounts, and cross-site request attacks.

Fix Add password length checks, per-IP/account throttling, CSRF tokens, Secure cookies in production, and a POST-only logout. Add security headers including CSP, frame restrictions, and Referrer-Policy.

Evidence: app/routers/auth.py:44–113

4

Separate encryption and session secrets

Medium

Problem The same SECRET_KEY signs sessions and derives the Fernet key used to encrypt provider tokens.

Impact Routine session-key rotation would make stored provider tokens unreadable, while a single secret compromise affects both systems.

Fix Introduce a dedicated, versioned encryption key and support staged key rotation. Keep the JWT signing key independent.

Evidence: app/services/crypto.py:8–13, app/services/auth.py:17–23

Scheduling and delivery reliability

5

Give failed one-time sends a real retry state

High

Problem A failed one-time send is returned to pending after its APScheduler date trigger has already been consumed.

Impact The message can remain pending forever, or be resent unexpectedly after a quick restart. Users cannot trust the displayed state.

Fix Use explicit states such as running, failed, and retry_scheduled. Record attempts separately, define bounded exponential retries, and add an idempotency key per recipient attempt.

Evidence: app/services/scheduler.py:79–89, app/services/scheduler.py:99–127

6

Schedule recurring jobs in the user’s timezone

High

Problem Local recurring times are converted to UTC using today’s offset and then permanently scheduled in UTC.

Impact A 09:00 local schedule can shift by an hour when daylight-saving rules change, or immediately use the wrong seasonal offset.

Fix Store the local wall-clock schedule and IANA timezone. Construct CronTrigger with that timezone and convert only concrete execution timestamps to UTC.

Evidence: app/routers/jobs.py:214–230, app/services/scheduler.py:112–123

7

Make multi-recipient delivery independently retryable

Medium

Problem One failed recipient marks the whole job failed even when other groups succeeded. A manual retry can send duplicates to successful groups.

Fix Store one delivery attempt per job and recipient, display partial success, and retry only failed recipients.

Evidence: app/services/scheduler.py:57–80

8

Validate schedules before committing jobs

High

Problem Trigger types, dates, and raw cron expressions are not fully validated before the job is committed. Scheduler registration happens after multiple commits.

Impact Invalid input can produce a server error or leave a partially configured job in the database.

Fix Parse and validate all trigger fields first, restrict enumerations, validate date ranges and DST gaps, then save the job and recipients in one transaction.

Evidence: app/routers/jobs.py:262–300

Data integrity and uploads

9

Protect uploaded media

High

Problem Uploads are checked only by filename extension, read entirely into memory, named with timestamps, and exposed from a public static route. Images are sent upstream using a hard-coded JPEG MIME type.

Fix Stream with a byte limit, inspect actual file signatures, assign random UUID names, preserve the correct media type, and serve files through an authenticated ownership-checked endpoint.

Evidence: app/routers/jobs.py:51–66, app/main.py:143, app/services/sender.py:22–34

10

Adopt versioned database migrations

Medium

Problem Handwritten migrations catch broad exceptions and silently continue. Migrations also run in both the Fly release command and application startup.

Impact Production can start with a partially migrated schema, making failures difficult to diagnose or recover.

Fix Use Alembic, keep every migration reversible, fail deployment on migration errors, and run migrations in one controlled place.

Evidence: app/database.py:31–81, fly.toml:22–23

Quality, operations, and maintainability

11

Add end-to-end workflow coverage

Medium

Current All 17 tests pass, but most cover small service functions and API-key behavior.

Add tests Token ownership, signup and session behavior, job CRUD, invalid schedules, DST transitions, upload validation, scheduler restart recovery, partial group failure, CSRF, and authorization boundaries.

Evidence: tests/

12

Make dependency builds reproducible

Medium

Problem Dependencies use open-ended minimum versions, so identical source can deploy different packages over time. Production also installs pytest.

Fix Generate a reviewed lock or constraints file, automate dependency updates, separate development dependencies, and use a smaller production image.

Evidence: requirements.txt, Dockerfile

13

Define the single-instance scaling boundary

Medium

Current One in-process scheduler and one SQLite volume work for the current single Fly machine.

Risk Adding workers or machines can duplicate sends, while the attached SQLite volume limits horizontal scaling.

Fix Document the one-instance invariant now. Before scaling, move scheduling to a single elected worker or durable queue and migrate shared state to PostgreSQL.

Evidence: app/main.py:125–128, fly.toml:7–16

14

Add structured operational visibility

Lower

Improve Emit structured logs with job and attempt IDs, expose a health/readiness endpoint, track send latency and failure categories, and alert when the scheduler stops or failed deliveries spike.

15

Keep documentation aligned with behavior

Lower

Problem The README still describes image-only 5 MB uploads, while the application accepts images and videos up to 50 MB. Some architecture and file-size descriptions are also stale.

Fix Update feature documentation alongside code and add a lightweight documentation consistency checklist to pull requests.

Evidence: README.md:31, app/routers/jobs.py:34–37

Can whatsend integrate with WhatsApp directly?

Yes—through Meta’s supported WhatsApp Business Platform Cloud API. Reverse-engineering the private protocol used by WhatsApp Web is a different path and should not be used for this production service.

A

Preferred path: Meta Cloud API adapter

Investigate

Feasibility Meta’s current documentation lists messaging, calls, and the ability to create, manage, and message WhatsApp group conversations. That makes a direct provider adapter technically relevant to whatsend’s core group-scheduling use case.

Benefits Remove the Whapi dependency and markup, use a supported integration, receive delivery updates through webhooks, and reduce exposure to undocumented protocol changes.

Verify Confirm group API eligibility, onboarding and business-verification requirements, supported group operations, template and consent rules, pricing, media limits, and rate limits for the intended accounts and countries.

Design Keep the existing sender interface and add a MetaCloudSender. Store provider-specific credentials separately, normalize delivery responses, and introduce a webhook endpoint with signature verification and replay protection.

Official source: Meta — WhatsApp Business Platform Cloud API

B

No-go path: reverse-engineered WhatsApp Web APIs

Do not ship

Meaning This would imitate a linked WhatsApp Web device by using undocumented endpoints and protocol behavior. It is often described as an “unofficial API,” not an API WhatsApp makes available for integration.

Risks Account bans, forced logouts, QR-session churn, silent breakage after WhatsApp updates, difficult encryption maintenance, weak delivery guarantees, and a larger security burden around session credentials.

Terms WhatsApp’s current consumer and business terms prohibit reverse engineering, unauthorized automated access, scraping, and unauthorized APIs that substantially reproduce the service. This is a contractual and operational risk in addition to the engineering risk.

Boundary Do not build, distribute, or operate this path for production accounts. A legal review would be required before even a controlled research prototype; it should never use real customer data or production phone numbers.

Official sources: WhatsApp Terms of Service · WhatsApp Business Terms

C

Decision spike: prove the supported route first

Plan

Week 1 Create a Meta test business account and number, verify group availability for the account, and send text plus media to a test group.

Week 2 Implement a thin MetaCloudSender, delivery-status webhook, credential model, and contract tests alongside the existing Whapi adapter.

Decision Compare supported features, onboarding friction, per-message cost, delivery reliability, and operational effort. If the Cloud API meets the group requirements, migrate gradually behind a provider flag; otherwise retain Whapi while documenting the missing official capability.

Recommended implementation roadmap

Sequence the work so security boundaries are closed first, delivery semantics become trustworthy second, and operational maturity follows.
