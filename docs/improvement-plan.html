Logic and delivery reliability

A scheduler is judged by duplicate prevention and explainable state. These changes make each run independently traceable and safe under retries, restarts, and slow upstream calls.

1

Model delivery runs instead of storing retry state on the job

P0

WhyA recurring APScheduler job and its separately named retry job can execute concurrently. Both mutate the same retry_count, retry_at, and retry_group_ids, so a new scheduled run can overwrite an older run’s retry state.

ChangeAdd delivery_runs with an immutable scheduled timestamp, status, lease, and idempotency key. Attach attempts and retries to a run; enforce a unique key such as (job_id, scheduled_for, group_id, attempt_number). Use one per-job lock/lease across primary and retry execution.

  • A slow cron run and a retry cannot send the same recipient twice.
  • Restarting during a send produces a recoverable run, not ambiguous job state.
  • The UI can explain which recipients succeeded, failed, or are retrying for each run.

Evidence: scheduler.py:64–89 and 92–176; retry state currently lives in job.py:36–38.

2

Remove upstream API calls and database repairs from GET pages

P0

WhyThe jobs list calls Whapi when group names are missing and writes the repaired names during a GET. Create/edit pages also fetch groups serially before rendering. A slow provider therefore makes core navigation slow and failures are silently swallowed.

ChangeCreate an account-scoped group cache with synced_at, an explicit “Refresh groups” action, a short timeout, and visible stale/error states. Render forms immediately from cached groups and refresh asynchronously.

  • Jobs list performs no external network calls and no writes.
  • Create/edit pages render within the local database latency budget.
  • Provider failures show an actionable message while manual group entry remains available.

Evidence: jobs.py:187–215 and 226–243.

3

Centralize validation and scheduling policy

P1

WhyLarge form handlers accept unbounded labels, messages, group arrays, and group names. Duplicate group IDs can create duplicate sends. Monthly days 29–31 also need a clearly documented “skip missing months” rule.

ChangeIntroduce typed command models shared by create/edit/API paths. Normalize and deduplicate recipients, cap recipient count and message length, validate WhatsApp group IDs, and make minimum recurrence/quiet-hour policy explicit. Store next_run_at and last_run_at for consistent UI and recovery.

Evidence: the form boundary begins at jobs.py:294; schedule construction is in 250–290.

4

Separate scheduling, sending, and persistence responsibilities

P1

ChangeSplit the 700+ line jobs router into command/service modules: form parsing, schedule policy, media storage, job repository, provider group sync, and delivery orchestration. Keep routers thin and make state transitions an explicit enum/state machine.

BenefitUnit tests can exercise state transitions without FastAPI forms or a live scheduler, and provider-specific behavior stops leaking into page handlers.

Evidence: app/routers/jobs.py currently owns upload storage, cron parsing, remote group discovery, CRUD, scheduler mutation, and presentation helpers.

Security and abuse resistance

The project has a good browser-security foundation. The remaining work is mostly revocation, quotas, distributed enforcement, and operational secret hygiene.

5

Add session revocation and active-user verification

P0

WhyAuthenticated pages trust JWT claims until expiry and do not reload the user. Disabling an account or changing a password does not invalidate other existing sessions.

ChangeAdd session_version or a sessions table, include the version/JTI in JWTs, and validate it against the user on protected requests with a short cache. Increment it on password change, account disable, or “sign out everywhere.”

Evidence: auth.py:33–47 trusts decoded claims; password changes occur at 229–243.

6

Protect API keys, sends, and webhooks with shared limits

P1

WhyOnly signin/signup use the in-memory limiter. API-key verification performs an expensive bcrypt check, sends have no per-key quota, and webhook bodies are read without an application limit. In-memory counters reset on restart and cannot support multiple processes.

ChangeAdd per-IP and per-key token buckets for authentication, group listing, sending, and webhooks; enforce body limits at the proxy/app boundary; return Retry-After; add API-key scopes and optional expiry. Move limits to Redis or another shared store before horizontal scaling.

Evidence: rate_limit.py:8–36, api.py:85–143, and webhooks.py:25–35.

7

Tighten CSP and dependency delivery

P1

WhyCSP nonces are present, but style-src 'unsafe-inline' remains necessary because templates contain many inline styles. HTMX is loaded from a third-party CDN on every page.

ChangeMove inline styles and page scripts into versioned static files, self-host the pinned HTMX asset, remove unsafe-inline, and add an automated CSP/security-header regression test.

Evidence: CSP is assembled in main.py:124–128; shared inline code begins at base.html:59.

8

Make key rotation and audit events first-class

P2

ChangeRequire a dedicated encryption key in production, support an ordered key ring with key IDs, re-encrypt tokens after successful fallback decryption, and log security events for login failures, API-key changes, token changes, exports, and destructive job actions.

AlsoRedact upstream response bodies and identifiers in logs by policy; set retention limits for logs and delivery attempts.

Evidence: token encryption currently falls back to the session secret in crypto.py:14–20.

UI, mobile, and accessibility

The refreshed dashboard, RTL support, dark mode, keyboard focus styling, and responsive job cards are strong foundations. The next pass should simplify navigation and make async states and dialogs accessible.

9

Turn the wrapped mobile nav into a deliberate menu

P1

ChangeUse a compact mobile header with a labelled menu button, current-page indicator, and grouped secondary actions for language, theme, timezone, profile, and sign-out. Keep the primary “New job” action visible.

MeasureNo two-row wall of navigation links at 320–768 px; all controls have at least 44 px touch targets and a visible focus state.

Evidence: base.html:14–35 and current wrapping behavior in app.css:388–424.

10

Finish the accessible interaction layer

P1

ChangeGive the confirmation modal role="dialog", aria-modal, focus trapping/restoration, and labelled buttons. Add aria-live to toasts and validation summaries, accessible names to icon-only theme/chip controls, loading announcements, and prefers-reduced-motion fallbacks.

TestKeyboard-only flows for sign-in, job creation, delete confirmation, filters, menus, and language switching; automated axe checks for representative English and Arabic pages.

Evidence: modal markup and behavior are in base.html:48–115; chip remove controls are created in form.html:215–238.

11

Make job creation a previewable workflow

P1

ChangeAdd a sticky summary showing recipients, message/media preview, timezone, next three occurrences, and DST/month-end behavior. Preserve entered values after server validation errors, show upload progress, and disable repeat submissions.

BenefitUsers confirm exactly what will be sent, where, and when before committing—reducing the most expensive class of product error.

12

Consolidate the front-end foundation

P2

ChangeSplit the 500+ line stylesheet into tokens, layout, components, and page modules; remove inline style attributes; move shared scripts from templates to static modules; and document component patterns for buttons, fields, badges, empty states, tables, dialogs, and feedback.

GuardrailKeep the zero-build-step approach unless bundle complexity clearly justifies a toolchain. A small server-rendered product does not need a SPA rewrite.

Evidence: app/static/css/app.css and app/templates/base.html.

Feature opportunities

Build these after run-level reliability is in place. They reuse existing jobs, attempts, tokens, localization, and provider adapters rather than creating parallel concepts.

13

Delivery center and actionable alerts

P1

Add a run-centric delivery view with recipient status, provider error categories, latency, retry countdown, and “retry failed recipients” action. Offer failure notifications by email or signed outbound webhook, plus daily/weekly delivery summaries.

14

Templates, drafts, and safe personalization

P2

Add reusable message templates and drafts, with previewed variables from an allow-list such as group name and scheduled date. Validate expansion length and show the final per-recipient payload before scheduling.

15

Schedule controls for real operations

P2

Add quiet hours, holiday exclusions, start/end dates, pause windows, bulk pause/resume, schedule export, and an upcoming calendar. For high-impact sends, add optional maker/checker approval.

16

Provider-ready architecture

P2

Promote sender capabilities into an explicit interface—text, media types, group discovery, delivery receipts, limits, and normalized errors. Keep the Meta adapter behind a flag until account eligibility and webhook contracts are proven; make whapi_base_url flow through the sender factory for testability.

Recommended delivery roadmap

Sequence work by risk reduction and dependency. Estimates assume one engineer familiar with the codebase and include tests.

Phase 0 · 2–3 days

Quick controls

  1. Cap/deduplicate inputs.
  2. Add API and webhook limits.
  3. Expose group-fetch errors.
  4. Add dialog/toast ARIA fixes.
Phase 1 · 1–2 weeks

Trustworthy runs

  1. Add delivery-run schema.
  2. Add leases and idempotency.
  3. Isolate retry state.
  4. Add concurrency/restart tests.
Phase 2 · 1 week

Fast, clear workflow

  1. Cache and refresh groups.
  2. Add schedule preview.
  3. Improve mobile navigation.
  4. Extract static UI assets.
Phase 3 · 1–2 weeks

Product leverage

  1. Delivery center and alerts.
  2. Templates and drafts.
  3. Quiet hours/calendar.
  4. Provider capability contract.
Scaling gateDo not run multiple application processes or machines while SQLite and the in-process scheduler own execution. Before horizontal scaling, move scheduled execution to a single elected worker or durable queue, use PostgreSQL/shared state, and replace in-memory rate limits.
